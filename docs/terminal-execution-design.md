# Terminal execution design

**Status:** One assistant-facing `run_terminal_command` tool, deterministic tier classification, Tier 2 approval, and a scoped Bubblewrap runner exist. The tool is disabled unless `TERMINAL_COMMANDS_ENABLED=true`. The older preview-only window demo remains available with `.venv/bin/python -m terminal.approval_demo` and never executes an operation. No privileged helper exists.

## Implemented command policy and execution

- `run_terminal_command` accepts one Fish command and an optional working directory. The model does not send a risk tier. The app resolves the working directory beneath `TERMINAL_WRITE_ROOT` and classifies the command. Inside the sandbox, `HOME` and `~` refer to that configured root. The tool result includes `access_root` and `sandbox_home`; this matters during development when the root is set to the repository instead of the host home.
- Tier 1 is limited to simple commands from a fixed read-only catalog (`cat`, `df`, `file`, `free`, `grep`, `head`, `ls`, `ps`, `pwd`, `stat`, `tail`, `uname`, `uptime`, and `wc`) whose executables resolve under `/usr/bin`. These run as direct argv without a shell and with the configured root mounted read-only.
- Under the default tier mapping, mutating commands, shell syntax, and commands the policy does not recognize go to Tier 2. **A well-formed unknown command requests local approval by default; unknown status alone does not deny it or execute it.** The approval is bound to the exact command and working directory. If approved, Fish executes it with write access only to `TERMINAL_WRITE_ROOT`.
- Under the default mapping, known Tier 3 command names, including `sudo`, `su`, `doas`, `pkexec`, destructive filesystem tools, and system power controls are denied. The application never adds privilege escalation. Root system paths are mounted read-only and the sandbox has no capabilities. Network is isolated by default; requesting network access cannot be downgraded below Tier 2 approval and appears in the approval dialog. System-level writes remain unavailable.
- The command runner mounts only system runtime paths and the configured user root. It masks `.env` files (except `.env.example`), common credential files/directories, and `.git/config`. It uses a clean environment, process/resource limits through `prlimit`, a 30-second wall and 29-second CPU limit, a 256 MiB per-file limit, a 64 MiB `/tmp`, and an 8 KiB combined output cap. If Bubblewrap, Fish, `prlimit`, required mounts, or namespace setup is unavailable, execution fails closed; there is no host fallback.
- The risk classifier is conservative for simple known commands, but it cannot prove arbitrary Fish programs harmless. Unrecognized commands are Tier 2 by default and require review unless the local mapping changes that. Tier 3 detection is a deny list, not a complete semantic analysis of every script or interpreter. Approval is bound to the exact source shown in the dialog, while the sandbox limits its reachable files and privileges.
- The default `.env.example` keeps terminal execution disabled. For this development checkout, `.env` is configured to enable it with the Jarvis project as its access root. A normal installation uses `~/` as the configured base write root after the user opts in.
- `TERMINAL_TIER_1_OVERRIDE`, `TERMINAL_TIER_2_OVERRIDE`, and `TERMINAL_TIER_3_OVERRIDE` map each classified source tier to an effective tier from 1 to 3. Defaults preserve the ordinary mapping. Any mapping is accepted: for example, Tier 3 to Tier 1 removes approval and denial routing for commands classified Tier 3. This affects approval policy only; the Bubblewrap filesystem root and lack of host privileges remain. A source Tier 2 or Tier 3 command mapped to Tier 1 still runs through Fish with write access inside the configured root. Network requests cannot be mapped below Tier 2 approval; mapping them to Tier 3 denies them. Invalid values prevent terminal-service startup. Restart Jarvis after changing `.env`.
- Approval state is in memory, requests expire after 90 seconds, and at most eight requests may be pending or approved at once. The assistant cannot call approval methods. Tool output is treated as untrusted data.

## Approval UI contract

The UI adapter displays the operation ID, validated arguments, trusted preview, affected resources, and remaining approval time. Approve and Deny actions call `approve_from_ui` and `deny_from_ui`. Assistant tools must not receive the queue or these methods. Approval is bound to one request ID and can be consumed once; denied, expired, or consumed requests cannot be reused. The dialog uses the system-installed `zenity` executable without a shell and passes only desktop-session environment variables; if Zenity or a display is unavailable, the request remains unapproved.

`TERMINAL_APPROVAL_FLOATING` accepts `auto`, `always`, or `never` and defaults to `auto`. Auto mode checks `HYPRLAND_INSTANCE_SIGNATURE`, `XDG_CURRENT_DESKTOP`, and `XDG_SESSION_DESKTOP`. When Hyprland and `hyprctl` are available, the adapter matches the Zenity PID and fixed approval-window title, then requests floating by that window's validated address. It tries the legacy dispatcher syntax first and the Lua dispatcher syntax used by newer Hyprland versions if that fails. It does not change Hyprland configuration or target the active window. If detection or matching fails, the dialog still works using the compositor's normal layout.

The queue does not authenticate a person or secure a future UI transport. UI integration must keep approval actions local to the interactive desktop, render arguments as escaped text rather than markup, and never treat assistant output or voice transcription as the user's approval.

Because the normal voice loop is always listening, a spoken confirmation is not an approval mechanism. If the local UI is unavailable, Tier 2 work must remain pending and expire without running.

## Validation limits and follow-up

Bubblewrap, Fish, and `prlimit` are system executables, not Python dependencies. `setup.sh` checks for them and warns when missing, but does not install packages. The current execution environment permits a scoped writable bind mount but rejects creation of a network namespace with `Operation not permitted`; the command runner therefore fails closed here. Do not remove network isolation or fall back to host execution to work around that restriction. Validate the full runner on the target desktop where unprivileged user and network namespaces are available.

Secret masking covers common credential names and stores, not arbitrary user-defined secret files. Keep custom secrets outside the configured access root. Tier 3 classification also cannot guarantee detection of destructive behavior hidden in arbitrary scripts; do not treat an approval prompt as proof that such a script is safe. Keep the writable root narrow during development and review the exact command before approval.
